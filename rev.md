# Архитектурное ревью mcp_mtproto

Дата: 2026-10-05. Объект: текущая рабочая копия, включая незакоммиченные изменения и app/export.py.

Проект небольшой, и модульная архитектура одного процесса соответствует его задачам. Основные дефекты связаны с владением общей Telegram-сессией, конкурентным доступом к файлам, границами разрешённых действий и восстановлением после сбоев. Для надёжного использования сначала необходимо устранить P1.

P1 — исправить до регулярного использования; P2 — исправить для надёжности и соответствия заявленному контракту. Оценка учитывает локальное использование одним владельцем аккаунта. P0 не обнаружены в проверенном объёме.

## P1

### 1. Чистая установка не запускает сервер

Источники: [requirements.txt](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/requirements.txt:1), [server.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/server.py:21).

`mcp>=1.2` разрешает несовместимую основную версию. На момент проверки устанавливается mcp 2.3.0, в котором `mcp.server.fastmcp.FastMCP` удалён. Воспроизведён ModuleNotFoundError при импорте app.server. Это ошибка действующего пути установки, а не только потенциальный риск обновления.

Исправление: для текущего кода ограничить MCP веткой 1.x и зафиксировать проверенный набор зависимостей. Переход на MCP 2.x проводить отдельно с проверкой совместимости. В CI проверять чистую установку и настоящий initialize/tools/list по stdio.

### 2. У общей Telegram-сессии нет единственного владельца

Источники: [client.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/client.py:40), [server.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/server.py:71).

Каждый вызов создаёт новый TelegramClient с одним и тем же SQLite-файлом. MCP SDK обрабатывает запросы конкурентно. Два инструмента, два MCP-хоста либо CLI вместе с сервером могут одновременно писать в session.session. На двух реальных SQLiteSession с синтетическими сущностями воспроизведено `sqlite3.OperationalError: database is locked`. Ожидание SQLite синхронное и способно задержать весь event loop. README предлагает закрыть Claude перед CLI, но это не предотвращает параллельные вызовы внутри одного сервера.

Исправление: один TelegramClient на жизненный цикл сервера; межпроцессная блокировка владельца сессии для CLI/других хостов. Если несколько хостов должны работать одновременно — один локальный процесс, владеющий сессией, к которому они обращаются. Для операций над одним ботом дополнительно нужна собственная очередь.

### 3. Конкурентные загрузки могут опубликовать повреждённый файл с ok=true

Источник: [server.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/server.py:285).

Оба запроса одного сообщения используют одинаковый `<id><ext>.part`. При открытии вторым запросом файл обнуляется. Первый запрос может затем переименовать общий файл, а второй продолжить запись в уже опубликованный inode либо упасть. Удаление старого пути .part не исправляет опубликованный файл.

Воспроизведение: два запроса скачивали один синтетический файл; второй прервался. Первый вернул ok=true, но конечные байты стали `A\x00\x00BBB` вместо `AAABBB`.

Исправление: блокировка по `(chat_id, message_id)`, отдельный временный файл каждой операции, проверка ожидаемого размера и атомарная публикация. Перед повторным использованием кеша нужно подтвердить завершённость файла.

### 4. send_to_bot разрешает отправку обычным пользователям и в чаты

Источник: [server.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/server.py:350).

После resolve_entity нет проверки `isinstance(entity, User) and entity.bot`. Название и описание обещают работу с ботами, но переданный ID человека или группы проходит к send_message. На подставном клиенте подтверждена отправка объекту User(bot=False).

Исправление: проверять получателя перед любым действием с побочным эффектом. Применить единый resolve_bot к инструментам работы с ботами. Если отправка людям нужна как функция продукта, она должна иметь отдельный явный контракт.

## P2

### 5. Идентификатор экспорта не уникален

Источник: [export.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/export.py:153).

Каталог содержит время только до секунды, а mkdir(exist_ok=True) разрешает его повторное использование. Два экспорта одного чата, начатые в одну секунду, пишут в одни .part и итоговые пути. Даже последовательные короткие вызовы могут заменить предыдущий результат. Воспроизведено с фиксированным временем: путь первого результата сохранился, содержимое было заменено вторым экспортом.

Исправление: уникальный job_id/UUID или атомарное создание каталога через mkdtemp. Время оставить читаемым префиксом. Прежняя ошибка перезаписи месячного файла между обычными запусками в текущей версии уже устранена; это отдельная оставшаяся коллизия.

### 6. Ответы ботов не связаны с конкретной командой

Источники: [server.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/server.py:357), [click_button](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/server.py:438).

Обработчик принимает любое новое сообщение от отправителя. При двух запросах одному боту один ответ удовлетворяет оба ожидания; фоновое уведомление тоже может быть принято за ответ. На двух конкурентных send_to_bot подтверждено присвоение одного сообщения обеим командам.

Исправление: сериализация диалога по bot_id; учитывать время/ID отправленной команды и reply_to, когда бот его предоставляет; отделять несвязанные события. Telegram не гарантирует reply_to у каждого бота, поэтому одну проверку поля нельзя считать полной корреляцией. Обработчики нужно снимать в finally, особенно после перехода к постоянному клиенту.

### 7. Ошибка при получении клиента оставляет соединение без cleanup

Источник: [server.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/server.py:77).

_get_client вызывается до try/finally каждого инструмента. Если connect или is_user_authorized выбросит исключение/получит отмену, код вызывающей стороны ещё не владеет клиентом. Disconnect выполняется только в отдельной ветке «не авторизован». Воспроизведено исключение проверки авторизации: disconnect не вызван.

Исправление: жизненный цикл через async context manager или MCP lifespan, покрывающий и получение ресурса. Аналогично защитить первичный вход в auth.py и получение клиента CLI.

### 8. Долгие выгрузки не восстанавливаются после FloodWait и таймаута

Источники: [export.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/export.py:161), [flood.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/flood.py:35).

retry_on_flood оборачивает отдельные RPC, но не iter_messages/iter_dialogs/iter_participants. У проверенной версии Telethon встроенное ожидание по умолчанию ограничено 60 секундами. Более длинный FloodWait прерывает итерацию; экспорт удаляет подготовленные части. Воспроизведён FloodWait(120) после частичной выдачи: экспорт завершился ошибкой без результата для продолжения.

При этом собственный retry_on_flood может спать произвольно долго внутри MCP-запроса, не учитывая оставшееся время клиента. Повтор большой операции начинает всё сначала. Перенос запуска в CLI снимает MCP-таймаут, но не добавляет восстановление.

Исправление: сохранять job_id, диапазон и последний обработанный message_id, получать историю страницами, продолжать после ограничений без повторной обработки. Для больших задач — start/status/cancel/result и согласованный бюджет времени. Коротким запросам возвращать структурированный retry_after, когда ждать внутри вызова нецелесообразно.

### 9. Права доступа к session выставляются после успешного входа

Источники: [auth.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/auth.py:19), [client.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/client.py:41).

Telethon создаёт SQLite-файл до chmod; chmod вызывается только после start/get_me/disconnect. При прерывании или исключении он не выполняется, а ошибки изменения прав игнорируются. Проверено: при umask 022 новый каталог получает 0755, session — 0644. Если родительские каталоги доступны другим локальным пользователям, они могут читать файл. Фактическая доступность зависит от прав родительских каталогов и ACL.

Исправление: на POSIX создавать закрытый каталог 0700 и файл 0600 до помещения в него сессионных данных, проверять права существующей сессии. Для Windows отдельно учитывать ACL; chmod не заменяет их.

### 10. Документация неверно описывает границу приватности

Источник: [README.md](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/README.md:6).

Утверждение «никакие данные никуда не отправляются; всё остаётся на диске» не соответствует назначению MCP. Сервер отдаёт тексты сообщений, участников и другие данные MCP-хосту. Хост может передавать их облачной модели в соответствии со своими настройками. Локальный транспорт stdio этого не исключает.

Исправление: описать фактический поток Telegram → локальный сервер → MCP-хост → выбранный провайдер модели, если хост его использует. Отдельно описать локальное хранение session/media/exports. Это исправление пользовательского контракта, а не утверждение о скрытой отправке данных самим сервером.

### 11. Лимиты частей экспорта не учитывают полный файл

Источник: [export.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/export.py:113).

Счётчики учитывают сообщения, но не заголовок файла. Одно сообщение, которое само больше лимита, всё равно добавляется в пустой буфер. Подтверждено: при max_words=10 и max_bytes=60 получен файл из 19 слов и 84 байт. Очень маленькие положительные max_mb также могут превратиться в нулевой max_bytes после int().

Исправление: учитывать заголовок и кодирование при оценке части; валидировать конечное число байт и конечность max_mb; явно выбрать поведение для слишком большого сообщения — разбивать, отклонять либо помечать превышение в результате.

### 12. Публикация экспорта атомарна только для отдельного файла

Источник: [export.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/export.py:177).

Переименование набора частей находится вне try/cleanup. Ошибка второго os.replace оставляет первый .md и остальные .part, хотя операция завершилась ошибкой. Воспроизведено внедрением ошибки второго переименования. Набор не имеет признака завершённости, на который могли бы опереться пользователи или дальнейшая автоматизация.

Исправление: готовить весь набор в уникальном временном каталоге на том же томе и публиковать переименованием каталога; либо последним атомарно записывать manifest со статусом complete и использовать его как условие готовности.

### 13. Кеш медиа не замечает замену вложения в Telegram

Источник: [server.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/server.py:285).

Ключ кеша содержит chat_id/message_id, но не идентификатор самого media. После редактирования сообщения с заменой вложения код получает актуальные метаданные, затем возвращает старый локальный файл. В ответе окажутся MIME/size нового вложения и байты старого. Вывод по коду; онлайн-сценарий не выполнялся.

Исправление: сохранять media/document/photo id и ожидаемый размер вместе с кешем, проверять их при повторном запросе; при несовпадении скачивать заново.

### 14. Нижняя граница дат различается у истории и экспорта

Источники: [server.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/server.py:178), [export.py](/Users/oleksandrbykaluyk/work/AI/mcp_mtproto/app/export.py:161).

get_history сохраняет сообщения с date == since. Экспорт передаёт since как offset_date при reverse=True. Документация установленного Telethon определяет offset_date как исключающую границу и при reverse=True. Сообщения точно на границе могут отсутствовать в экспорте при том же диапазоне. Это вывод из кода приложения и контракта SDK; реальный Telegram не проверялся.

Исправление: определить единый интервал [since, until), выбирать немного более широкий диапазон и фильтровать границы локально; для продолжения выгрузки использовать ID, не только дату. Проверять since < until.

## Рекомендуемая структура

1. MCP-адаптер: схема параметров, ограничения, единый формат ошибок, аннотации побочных эффектов. Значения limit сейчас не имеют верхней границы, а результаты поиска и списков не содержат курсора продолжения.
2. TelegramService: один клиент на процесс, контроль владельца session, восстановление соединения, бюджет запросов, отдельная очередь операций каждого бота.
3. Export/Download service: уникальная операция, блокировки одинаковых ресурсов, проверяемый кеш, атомарная публикация.
4. Для долгих операций: сохранённое состояние задания, progress/status/cancel/result и продолжение по message_id. Для локального проекта достаточно локального хранилища состояния.
5. Проверки поставки: зафиксированные зависимости, проверяемые версии Python, чистая установка и stdio smoke test; тесты конкурентных вызовов, отмены, ошибки диска и восстановления.

Порядок: восстановить чистый запуск → ввести владение сессией и ограничения получателя → устранить гонки файлов → исправить корреляцию ответов и lifecycle → сделать долгие операции возобновляемыми → закрепить контракт и регрессионные проверки.
